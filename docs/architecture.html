Upload → searchable document → summary

The work completed on 3–4 October separates search readiness from summary readiness and carries section context into stored chunks. Example: a school handbook's “Late pickup” section continues on another page.

  1. Store and queue

    The authenticated upload stores the file in Supabase and enqueues BullMQ work. The API returns 202 with the document ID. Ingestion starts at PROCESSING; summary starts at PENDING.

  2. Read pages

    extractDocPages() returns page objects containing Markdown for PDF, DOCX, and images. TXT/Markdown uploads return one text object. The worker emits page_extracted with the complete extracted text.

  3. Track sections

    The heading stack persists across pages. “Late pickup” stays in the breadcrumb of ordinary continuation text. Section groups exist in memory; their IDs and paths are saved in chunk metadata. Heading formatting still needs validation.

  4. Create parents and children

    Each page part becomes parents of up to 1,200 characters with 200 overlap, then children of up to 400 with 50 overlap. Source text is separate from searchText: filename + section path + passage. Size settings count characters before the context prefix.

  5. Link and embed

    Parents link to previous/next parents in the same section. Children embed their full searchText into 384 numbers. A tokenizer checks at most 256 tokens; oversized input fails ingestion rather than silently losing text.

  6. Save and enable questions

    saveDocumentChunks() saves parents and children in a transaction. The worker sets status=COMPLETED, summaryStatus=PROCESSING, then emits chunks_ready. Questions can start now.

  7. Generate the summary

    The worker batches full extracted text, summarizes the batches, and saves a master summary. It sets summaryStatus=COMPLETED or FAILED. Summary failure leaves the searchable chunks available.

Question → evidence → answer

  1. Check access and input

    JWT and ownership checks protect document access. checkMaliciousIntent() screens input before the CRAG graph; accepted questions load conversation history.

  2. Choose the path

    Intent routes greetings to generation, summary requests to the saved summary with readiness checks, page requests to page chunks, and factual questions to decomposition.

  3. Split the question

    decomposeNode() creates up to four independent queries, then searches them sequentially. It does not insert facts found by one query into the next query.

  4. Search contextual children

    Vector and Postgres full-text search each collect up to 20 child hits. RRF returns up to 15 parent candidates per query. Single-document RRF uses 10; user-wide search uses 60 and filters owned completed documents. Full-text ranking uses ts_rank_cd, not BM25.

  5. Rerank and expand

    Cohere chooses up to three parent searchText passages per query. Parent IDs are deduplicated. Immediate same-section previous/next parents are added, capped at 24 total parents; expansion is not recursive.

  6. Grade or retry

    One grading call evaluates the combined evidence against the original question. Any retained evidence proceeds to generation. With none, rewrite the original question into one alternative query. Three retrieval rounds maximum, not three retries for each subquery. Grader errors currently retain the evidence.

  7. Generate and deliver

    Generation receives contextual passages, history, and page citations, with untrusted input wrapped in random tags. The completed answer is sent as word events and saved as a message. A relevance decision does not guarantee a correct or complete answer.

What can be inspected

GET /api/documents/get-all-parent-chunk/:docId returns owned parents with raw/contextual text, metadata, links, and child counts. GET /api/documents/get-all-child-chunk/:parentId returns their children, vectors, dimensions, and embedding diagnostics. Rebuild section groups from the saved metadata.

Parent / child metadata:
document_title (filename), heading_path, section_id, section_part_index,
page_number, source_pages, chunk_index, chunker_version
Child additions: child_index, embedding diagnostics
Parent links: prevParentId, nextParentId (same-section reading order)

GET /api/documents/progress/:docId emits live extraction, heading, section, chunk, link, embedding, save, and readiness events. Chat emits candidates, reranked selections, neighbor additions, grading decisions, and final generation context. Event IDs and timestamps help correlate the events with console logs.

Beyond the reference

  • Contextual children feed hybrid search; Cohere reranks parents, then immediate same-section neighbors expand the evidence.
  • The corrective loop grades the collection and rewrites only when no evidence remains, with at most three retrieval rounds.
  • Untrusted-text wrappers: retrieved text and questions sit inside random nonce tags in generateNode().
  • Live progress and detailed inspection: saved parent/child REST responses, upload SSE, chat retrieval events, and verbose console logs.
  • Separate chunk and summary readiness lets questions start before summary generation finishes.
