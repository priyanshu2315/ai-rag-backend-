System schematic · document intelligence

Parent‑Child RAG Pipeline

How a PDF becomes a cited, real-time answer — an ingestion pipeline that turns files into an indexed tree of chunks, and a retrieval pipeline where an agent decides for itself when to search. Plus the two techniques that were tried, measured, and quietly retired.

Express 5 Prisma 7 + pgvector BullMQ / Redis (Upstash) Supabase Storage LlamaParse Xenova MiniLM‑L6‑v2 Cohere Rerank Groq · GPT‑OSS 120B / 20B LangSmith
Live in production Implemented, then superseded

01  Ingestion

upload → indexed & summarized

A file becomes two parallel structures: an overlapping tree of parent and child text chunks for retrieval, and a distilled summary for orientation — all built off the request thread by a background worker.

1

Upload

Express 5MulterJWT

Client sends multipart form data to POST /api/documents/upload. Multer holds the file in memory only — it never touches local disk. Accepted types: PDF, DOCX, JPEG/PNG/WEBP, TXT/MD.

POST /api/documents/upload
upload.single("file")  // multer.memoryStorage()
2

Store the raw file

Supabase StoragePrisma / Postgres

The buffer is pushed to a private Supabase Storage bucket. A Document row is created immediately with status: PROCESSING — the API responds 202 without waiting for anything below.

bucket "documents"
path  {userId}/{timestamp}-{filename}
3

Enqueue the processing job

BullMQRedis · Upstash (TLS)

This is the Redis hop: a BullMQ queue named document-processing, backed by a managed Upstash Redis instance, decouples the slow parsing/embedding work from the upload request.

documentQueue.add("extract-and-embed", {
  documentId, filepath, mimetype
})
4

Worker picks up the job

BullMQ Worker

A Worker listening on the same queue (running in-process alongside the API) receives the job and drives every remaining ingestion step below.

5

Parse & extract text

LlamaParsepremium / OCR mode

The file is downloaded back from storage and parsed to Markdown. Scanned exhibits are OCR'd, tables become Markdown tables, and charts/diagrams are described as bullet points — per a custom parsing instruction. Plain .txt/.md skip parsing entirely.

LlamaParseReader({ premiumMode: true, resultType: "markdown",
  parsingInstruction: "transcribe tables as markdown, …" })
6

Split into parent chunks

RecursiveCharacterTextSplitter

Each page's text is split into large, context-rich chunks — these are what actually gets handed to the LLM at answer time.

new RecursiveCharacterTextSplitter({
  chunkSize: 1200, chunkOverlap: 200
})  // → ParentChunk rows, tagged {page_number, chunk_index}
7

Split into child chunks

RecursiveCharacterTextSplitter

Each parent is re-split into small, precise chunks. Search matches happen here — the match is then traced back up to its parent for context.

new RecursiveCharacterTextSplitter({
  chunkSize: 400, chunkOverlap: 50
})
8

Embed each child chunk

Xenova / Transformers.jslocal · CPU

Embeddings run in-process on CPU — no external API call, no per-token cost. Same model embeds both documents and, later, search queries.

pipeline("feature-extraction", "Xenova/all-MiniLM-L6-v2")
extractor(text, { pooling: "mean", normalize: true })  // → 384 floats
9

Store & index the vector

pgvectorHNSW · cosine

Prisma can't type a vector column, so the insert is raw SQL. A cosine-similarity HNSW index (plus btree indexes on document/page) makes the later search fast.

INSERT INTO "ChildChunk" (…, embedding) VALUES (…, '[0.012,…]'::vector)

CREATE INDEX … USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64)
10

Summarize the document

GPT‑OSS‑20Bvia Groq

Full text is batched to ~5,000 tokens (respecting paragraph/sentence boundaries) and summarized per batch; if there's more than one batch, a second call synthesizes them into one master summary. Result lands on Document.summary, and status flips to COMPLETED.

"Summarize the following document section
comprehensively using bullet points: …"
model: gpt-oss-20b · temperature 0

02  Retrieval & answering

question → cited answer

Not a fixed embed-then-answer pipeline — an agent with two tools, deciding turn by turn whether it needs to search at all, and with what query.

1

Chat request

POST /api/chatSSEJWT

Guarded before any LLM call runs: if the target document is still PROCESSING or FAILED, the request is rejected outright.

2

Assemble context

Postgres · Message table

Last 6 messages of chat history load alongside a system prompt that requires a search before answering factual questions, a [Source ID: Page N] citation on every claim, and forbids hallucinating.

3

Agent reasoning

GPT‑OSS‑120Bvia GroqLangSmith traced

Function-calling with two tools exposed: search the corpus, or fetch the pre-computed document summary. The model chooses.

search_corporate_database(search_query, page_number?)
get_document_summary()
4

Tool: hybrid search

pgvector cosinePostgres full-textRRF

The query is embedded with the same MiniLM model used for ingestion, then run two ways at once and fused — see Fig. 2.

5

Rerank

Cohere · rerank-english-v3.0

The 15 fused candidates are reranked against the actual query text; only the top 3 are returned to the agent as tool output.

cohere.rerank({ model: "rerank-english-v3.0", query, documents, topN: 3 })
6

Loop, bounded

max 5 iterations

The agent can re-search with a different query if the first result isn't enough. A previousSearches set blocks repeat queries; at 5 iterations, one forced final call answers with whatever's been gathered.

7

Stream the answer

Server-Sent Events

Events for status, tool start/finish, tokens, and completion are pushed over SSE; the assistant message is persisted once streaming ends.

03  Retired approaches

tried, measured, replaced — not deleted

Two LLM calls used to run before every search: one to classify what the user wanted, one to rewrite the question into a standalone query. Both functions still exist in the codebase — commented out — replaced in a single commit by the agent loop in Fig. 3, which folds intent detection and reference resolution into one tool-calling model instead of two extra round-trips.

Superseded

Intent classification

classifyIntent() — a dedicated call to the smaller model, forced into JSON, to route each message before anything else ran.

→ GREETING | GLOBAL_SUMMARIZE | SEARCH
model: gpt-oss-20b · forced JSON output
Superseded

Query rewriting

rewriteQuery() — resolved pronouns and folded chat history into one standalone query before it ever reached search.

"Rewrite the latest question into a standalone
search query. Resolve pronouns. Do not answer."
model: gpt-oss-20b

04  Stack reference

what runs where
API & auth
Express 5 · JWT + bcrypt · OTP-based password reset
Database & ORM
PostgreSQL + pgvector (Supabase-hosted) via Prisma 7
Queue
BullMQ over ioredis, Redis hosted on Upstash
File storage
Supabase Storage (private "documents" bucket)
Parsing
LlamaParse — premium mode, markdown + OCR output
Chunking
@langchain/textsplitters — RecursiveCharacterTextSplitter
Embeddings
Xenova/all-MiniLM-L6-v2 — local, 384-dim, CPU
Reranking
Cohere rerank-english-v3.0
Generation
GPT-OSS 120B / 20B served via Groq (OpenAI-compatible SDK)
Observability
LangSmith traces every agent call end-to-end

Every document and chat route sits behind JWT auth, checked per-request against the signed-in user — the two exceptions are a pair of unguarded debug endpoints left open for chunk inspection.
