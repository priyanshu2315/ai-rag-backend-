## Project map

- This repository is a Node.js ES-module Express backend for chat over uploaded documents. There is no frontend here. `server.js` mounts `/api/auth`, `/api/documents`, `/api/chat`, and `/api/health`, and starts the document worker.
- Code is organized as `src/routes` -> `src/controllers` -> `src/services` -> `src/repositories`; `src/config` holds clients and infrastructure. Auth uses JWT via `src/middlewares/auth.middleware.js`.
- Ingestion: upload to Supabase Storage, enqueue a BullMQ job in Redis, then `src/workers/document.worker.js` parses pages, creates parent/child chunks, embeds child chunks, stores them in PostgreSQL/pgvector, and summarizes the document. Progress uses Redis Pub/Sub and SSE.
- Chat: `src/services/chat.service.js` runs an input security check, loads history, invokes the LangGraph corrective RAG pipeline in `src/services/crag.service.js`, and streams an answer through SSE. Search and conversation persistence live in `src/repositories/chat.repository.js`.
- Database schema and migrations are in `prisma/`; Prisma Client is generated into `generated/prisma`. `src/config/db.js` uses the PostgreSQL driver adapter. Follow `PRISMA_WORKFLOW.md` for approved schema changes.
- For deeper context, read only the relevant sections of `PRODUCT.md`, `docs/chat-pipeline.md`, and `docs/delete-document-api.md`. Treat docs as orientation and verify details against current code.
- `npm test` is a placeholder that exits with an error; use relevant targeted tests when changes are authorized.

## Current pipeline (reviewed 5 October 2026)

- AI routing: `src/config/ai.js` exposes `getAI(task)` and `chatCompletion(task, options)` for `agent`, `chat`, `fast`, and `summary`. `AI_PROVIDER=mixed` enables per-task `AI_<TASK>_PROVIDER` and `AI_<TASK>_MODEL` overrides. Defaults route agent/chat/fast to Groq and summary to OpenRouter. A named global provider forces every task to that provider and ignores per-task model overrides. Providers currently include Groq, OpenRouter, OpenCode, and Gemini. Read the config rather than assuming a particular model; environment changes require process restart. Local embeddings and Cohere reranking are separate from this LLM routing.
- Two readiness states: `Document.status` tracks ingestion (`PROCESSING`, `COMPLETED`, `FAILED`); `summaryStatus` tracks summary generation (`PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`). The worker saves all chunks before setting `status=COMPLETED`, `summaryStatus=PROCESSING`, and emitting `chunks_ready`. Questions can then run while the summary is still being generated. Summary failure leaves searchable chunks available. Summary requests must check `summaryStatus` and saved summary content.
- Extraction: `aiService.extractDocPages()` returns objects whose `text` contains LlamaParse Markdown for PDF/DOCX/images. Plain text/Markdown uploads return one text object. The parsing prompt asks for tables, OCR, and consistent heading levels; these are requests to the parser, not structural guarantees.
- Chunking lives in `src/services/chunking.service.js`, called by the worker. Version `section-context-v1` carries a heading stack across page boundaries. It detects Markdown, standalone bold, and numbered uppercase headings, ignoring heading detection inside fenced code blocks. Sections are temporary groups, not a Prisma model. Each page part is split separately into parents of 1,200 characters with 200 overlap, then children of 400 characters with 50 overlap. A parent currently belongs to one page; section context and links can span pages.
- Parent and child `text` hold the source passage; required `searchText` prefixes the document filename and section breadcrumb. Metadata includes `document_title` (filename), `heading_path`, `section_id`, `section_part_index`, `page_number`, `source_pages`, zero-based global `chunk_index`, `chunker_version`, and child `child_index`. Identity is document-generic: never require a user-entered company name. A filename prefix is not a validated organization/title identity.
- Parent `prevParentId` / `nextParentId` link reading order only within the same detected section. They are nullable strings, not Prisma self-relations, and are not semantic links to referenced sections. Chunks are saved together in a transaction by `saveDocumentChunks()`.
- The worker embeds child `searchText` with `Xenova/all-MiniLM-L6-v2` into normalized 384-dimensional vectors. It checks the complete input with the model tokenizer against a limit of at most 256 tokens, rejects oversized input instead of silently truncating, and saves diagnostics in `metadata.embedding`. Oversized chunks currently fail ingestion; automatic resizing is not implemented.
- Search: child vector and PostgreSQL full-text search each gather up to 20 hits; RRF merges them into up to 15 parent candidates per query. RRF constants are 10 for a single document and 60 across a user's completed documents. This is `ts_rank_cd` full-text ranking, not BM25. Cohere reranks parent `searchText` to the top 3 per query. Parent IDs are deduplicated, then immediate same-section neighbors are added, capped at 24 total parents. Grading and answer generation use contextual `searchText` (saved summaries use their summary text).
- CRAG splits a search question into up to four independent queries and executes them sequentially; later queries do not use facts discovered by earlier searches. One batch grader evaluates the combined evidence. Any retained evidence proceeds to generation; rewriting occurs only when none remains. The rewriter uses the original question and replaces the query list with one alternative query. Limit: three retrieval rounds total, not three retries per subquery. Grader failure currently keeps retrieved evidence as a fallback; passing relevance does not prove that every requested fact is covered.

## Inspection and frontend handoff

- `docs/frontend-chunk-inspector.md` documents payloads and responses. Verify it against current code: its 24-hour Redis replay description is now stale. There is no frontend implementation in this repository.
- Authenticated inspection routes: `GET /api/documents/get-all-parent-chunk/:docId` returns stored parents with `text`, `searchText`, metadata, previous/next IDs, and `totalChildren`; `GET /api/documents/get-all-child-chunk/:parentId` returns the parent plus children with contextual text, metadata, vectors, and `embeddingDimensions`. Controllers check document ownership.
- `GET /api/documents/progress/:docId` streams extraction, heading decisions, section parts, parent/child creation, links, embedding diagnostics, save progress, and readiness. Events have document IDs, UUID event IDs, and timestamps. Since the latest storage-saving change, `uploadProgress.js` publishes live only: `getProgressHistory()` returns `[]` and clearing history is a no-op. Refresh cannot recover extracted pages or the old event timeline; rebuild saved section/parent/child views through REST. Do not present missing live page data as a measured zero.
- Chat emits `retrieval_candidates`, `rerank_result`, `neighbor_expansion`, `grading_result`, and `generation_context`, plus status/tool/answer events. Detailed traces are live; message persistence does not save the complete event trace. The answer is generated first, then sent as word events by `chat.service.js`.
- Verbose JSON logs use `[Document pipeline]`, `[Chunking]` (standalone chunker), and `[CRAG details]`. `RAG_DEBUG=false` suppresses those detailed logs, not every worker log. Events during `preparing` do not prove chunks have been saved.
