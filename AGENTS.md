## Project map

- This repository is a Node.js ES-module Express backend for chat over uploaded documents. There is no frontend here. `server.js` mounts `/api/auth`, `/api/documents`, `/api/chat`, `/api/roles`, `/api/users`, `/api/health`, and `/api/pipeline`, and starts the document worker.
- Code is organized as `src/routes` -> `src/controllers` -> `src/services` -> `src/repositories`; `src/config` holds clients and infrastructure; `src/utils/http.js` has `httpError(status, message)` and the `handle()` controller wrapper used by roles, users and chat conversations. Auth uses JWT via `src/middlewares/auth.middleware.js` (`requireAuth`, `requireAdmin`).
- Ingestion: upload to Supabase Storage, enqueue a BullMQ job in Redis, then `src/workers/document.worker.js` extracts pages, creates parent/child chunks, embeds child chunks, stores them in PostgreSQL/pgvector, and summarizes the document. Progress uses Redis Pub/Sub and SSE.
- Chat: `src/services/chat.service.js` runs an input security check, loads history, invokes the LangGraph corrective RAG pipeline in `src/services/crag.service.js`, and streams an answer through SSE. Search, neighbor expansion, and conversation persistence live in `src/repositories/chat.repository.js`. Hop-plan helpers live in `src/services/hop-evidence.service.js`.
- Database schema and migrations are in `prisma/`; Prisma Client is generated into `generated/prisma`. `src/config/db.js` uses the PostgreSQL driver adapter. Follow `PRISMA_WORKFLOW.md` for approved schema changes.
- For deeper context, read only the relevant sections of `PRODUCT.md`, `docs/chat-pipeline.md`, and `docs/delete-document-api.md`. Treat docs as orientation and verify details against current code.
- `npm test` is a placeholder that exits with an error; use relevant targeted tests when changes are authorized. `tests/crag-multi-hop.test.js` has 8 known failures (13 November): its search stub expects plain-string queries and its rewriter mocks return plain strings. `tests/hop-evidence.test.js` passes 17 of 17.
- `ROADMAP.md` is the user's 15-day plan (4-18 November 2026). Mark items there when they are verified done.

### Users, roles and document access (added 8-9 November)

- Model: one document library; only `ADMIN` users upload or delete. A `Role` is a name plus documents (`RoleDocument` link table); a user has any number of roles (`UserRole` link table). There is no direct document-to-user sharing and no cached user-document table. `User` has `name`, `type` (`ADMIN`/`USER`), `isActive`, `mustChangePassword`, `updatedAt`. `Document.userId` now only means "uploaded by" and is not used for access. Migration `20261108132923_add_roles_and_user_types` (applied 8 November with `prisma migrate deploy`; it also backfills `Conversation.type`).

No access answers 404, not 403.
- `requireAuth` loads the user from the database on every request: inactive or missing users get 401; while `mustChangePassword` is true every route except `POST /api/auth/change-password` answers `403 PASSWORD_CHANGE_REQUIRED`. `req.user` is `{ id, email, name, type }`. `requireAdmin` answers 403 for non-admins.

Email (9 November): `src/config/mailer.js` (nodemailer SMTP, Gmail defaults; env `EMAIL_USER`, `EMAIL_PASSWORD` as an app password, `EMAIL_FROM`, `APP_URL`, optional `SMTP_HOST`/`SMTP_PORT`) and `src/services/email.service.js` (`sendWelcomeEmail`, `sendTemporaryPasswordEmail`, `sendPasswordResetCode`; `send()` never throws and returns true/false). Summary requests must check `summaryStatus` and saved summary content.
- Extraction was reworked after 5 October. `aiService.extractDocPages()` calls `extractDocument()`, which uses the `extraction` AI task (Gemini by default) in page batches with a contents-outline pass (`src/services/document-outline.service.js`). After checking the first two v4 uploads (stress test and VAYUZ SOP; all values correct, old 5 October defects fixed except heading-only chunks), two more fixes were applied on 9 November: the Resolution reference rule now needs a number or code ("resolution within" / "Resolution SLA" were stored and then followed as override references), and the extraction prompt writes a header-less label/value block (owner, version, effective date) as "- Label: value" lines instead of a table (the VAYUZ cover table was stored as "Document Owner: Version"). Heading-only chunks at the foot of a page (ISGEC C15) remain open. Also open for real documents: a paragraph that continues onto the next page is cut at the page break into two parents (the chunker starts a new parent at every page), so a sentence can be split mid-date. The extraction prompt now keeps a company name printed above the title as a text line (9 November). Knowledge base for search work: `eval-docs/kb/` (50 synthetic Calderwick Pump Systems documents, `FACT-SHEET.md`, `ANSWER-KEY.md` with 31 questions, generator in `build/`), uploaded 9 November under the admin account. - Chunking now lives in `src/services/simple-chunking.service.js` (`buildDocumentChunks`, version `ai-corrected-markdown-v4` since the 9 November fixes; `v3` before), exposed through `aiService.buildDocumentChunks()`. It parses Markdown with remark/GFM and uses token budgets measured with the embedding tokenizer (parent 1,024, child 256). It builds a `document-identity-v1` identity (extracted title or filename fallback) and writes metadata including `chunker_version`, `table_ids`, `linked_table_ids`, `is_toc`, and `references`/`cross_references`. The old `chunking.service.js` and `section-context-v1` no longer exist. Heading rules, table-continuation logic, and the exact `searchText` format were not re-reviewed on 4 November; read the source before describing them.
- Parents and children keep `text` (source passage) and required `searchText` (contextual text used for search, reranking, grading, and generation). Parent `prevParentId`/`nextParentId` are nullable strings for same-section reading order, not Prisma self-relations or semantic references. Chunks are saved together in a transaction by `saveDocumentChunks()`.
- Child `searchText` is embedded with `Xenova/all-MiniLM-L6-v2` into normalized 384-dimensional vectors. Input is checked against a 256-token limit and rejected (`EMBEDDING_INPUT_TOO_LARGE`) instead of silently truncated.

### Hybrid search (`chat.repository.js`)

- A search query is a `{ text, keywords, identifiers, entities }` object (planner, grader `next_query`, and rewriter all produce this shape) or a plain string (eval scripts and fallbacks). `buildSearchTiers()` (exported) converts either form into:
  - `idPatterns`: identifiers of at least 3 characters as `%ID%` patterns.
  - `phraseQuery`: entities as adjacent-word tsquery phrases, e.g. `(new <-> zealand) | (audit <-> committee)`.
  - `wordQuery`: planner keywords, or every useful word of the text when no keywords are given, sanitized by `buildRelaxedTsQuery()` (stop words removed, terms joined with `|`, empty string when nothing useful remains).
- `searchSingleDocument()` and `searchAllUserDocuments()` run four child-level tiers, skipping a tier whose input is empty: vector (pgvector cosine distance), identifier (`"searchText" ILIKE ANY(...)`), phrase, and keyword (both `to_tsquery('english', ...)` ranked by `ts_rank_cd`). Each tier sorts by rank before its `LIMIT`. Table-of-contents chunks (`is_toc`) are excluded. This is not BM25.
- Weighted RRF with k=10 in both functions sums per parent: vector 1.0, identifier 2.5, phrase 1.5, keyword 1.0. The top `SEARCH_PARENT_CANDIDATES` parents are returned (all-documents search uses at least 20 candidates and tier limits of at least 30). All-documents search only uses `COMPLETED` documents from the `allowedDocumentIds` list passed in by chat (see Users, roles and document access).
- The final `SELECT` orders parents by `total_score`, so the Cohere-failure fallback (`chunks.slice(0, topN)`) keeps the best-scored candidates. Each candidate carries per-tier ranks (`vectorRank`, `identifierRank`, `phraseRank`, `keywordRank`) and `matchedBy`; counts are cast to `::int` to avoid BigInt serialization errors.
- Known limits: the identifier tier has no index, and its `ROW_NUMBER()` is ordered by child ID rather than relevance. Because `searchText` includes the filename prefix, an identifier that appears in a filename matches every chunk of that file.

### CRAG (`crag.service.js`)

- `analyze_intent` routes greeting -> `generate`, summary -> `fetch_summary`, page -> `fetch_page`, and other questions -> `decompose`.
- `decompose` (agent task) returns a hop plan (at most 12 hops with `dependsOn`) and starting queries. Rule 7 ("one hop = one lookup", added 7 November, reworded 8 November) splits the question at every relationship; when the question asks for a person's name, the hop that finds the person is worded "(the person's name, not only the role)" instead of adding a separate name hop, and optional "if needed" hops are forbidden. Its worked example (ticket T-88 -> team -> manager -> email) is deliberately unrelated to any test document. Rule 10 (8 November) says "who had to / must / is allowed to approve" questions need the case's deciding value plus the rule table, then an apply hop (generic PO-7731 example). Rules added 10-13 November: rule 2 (history only resolves references; do not copy codes, titles or answers from earlier replies), rule 6 (a starting query for every entry-point task), rule 7's exception (when the answer comes from a rule or limit table, add a last hop "find the person who held the role on the case's date"), rule 10's wording (rule tasks and queries use the rule document's words, without the case's category, amount or date, shown by a starting-query example "sign-off limits by value"), rule 11 (a rule check needs a rule hop, a facts hop and a compare hop, each naming the kind of value), rule 12 (a value the user states is a given, not a lookup; its example h1 is "find the purchase approval limits by value"). Models followed the examples, not the sentences. `getLeavePlanningInstructions()` is no longer used in any prompt (its import in `crag.service.js` is unused). Prompt rule 13 asks for `hopId` (the entry task the query is for), a short standalone `text`, 2-6 `keywords` without vague words, `identifiers` that name one record (not P1, clause, amendment or version labels), and multi-word `entities` without the asker's own company, with one worked example. Responses are normalized to objects (plain strings are still accepted) and entries without text are dropped. When the planner tags queries with `hopId`, code adds a query (the task text, first 20 words) for any entry hop without one, and puts one query per entry hop first; then queries are deduplicated by `queryKey(text)` and capped at `MAX_SUB_QUERIES` (3), so a fourth entry hop waits for a later round. There are two planning attempts; failure routes to `generate` with a `planning_failed` reply and never searches the raw question.
- `retrieve` runs all queries in parallel (`Promise.all`). Query `text` is used for the embedding, Cohere rerank, events, `allQueries`, and `searchRounds`. Only the repository receives the full object. Cohere (`rerank-english-v3.0`) reranks whole parent `searchText` to `RERANK_TOP_N` per query, ignoring search scores, and falls back to top search hits on failure. It returns scores only for the kept chunks. Collected parents keep Map insertion order, which depends on which parallel query finished first.
- `getParentNeighbors()` expands the first `EXPANSION_SEED_COUNT` collected parents, capped at `MAX_TOTAL_CHUNKS_PER_ROUND`. Each added parent records the expansion type in `retrievalOrigin.type`: `section_sibling` (prev/next), `section_lead` (when `section_part_index > 0`), `chapter_expansion` (when the question mentions process/step/flow/procedure/overview/policy/guide/sop), `table_continuation` (`table_ids`/`linked_table_ids`), and `reference_following` (only for override references like appendix/amendment, references cited in the question, or relevant table-of-contents/guide lines).
- `grade` (agent task) evaluates every hop in one batch and returns `relevant_chunk_ids`, per-hop `status`/`value`/`inputBindings`/`evidence` (chunk ID plus quote), and `next_query`. A LATER CHANGES rule also keeps chunks that amend or supersede a fact the question asks about, without changing the hop value; the answer prompt's precedence rule explains both. Rules added 10-13 November: VALUE KIND (a deadline is not an event date, a role is not a person, a count comes from the case's records), CURRENT SOURCE (use the version in force on the case's date), and exact quotes (whole lines in order, no added brackets or reformatting). Since 13 November the grader sees every chunk kept in earlier rounds (`accumulatedDocs`) plus the new round's chunks, so a hop whose facts arrive in different rounds can resolve; its input no longer contains `documentId` (it had cited a document ID as a chunk ID). The answer prompt gets a code-built VERIFIED ANSWER FACTS list (every resolved hop value, chain ends marked FINAL) just before the documents.
- `updateHopProgress()` in `hop-evidence.service.js` accepts a resolved hop only if `value` is non-empty, its dependencies were accepted, `inputBindings` match the dependency values (kept on purpose), at least one quote names a chunk the grader saw (quotes with unknown chunk IDs are dropped since 13 November; only valid quotes are stored), and every remaining quote passes `isQuoteInDocText()`. A quote passes when it is an exact normalized substring, when at least 80% of its line/`...` pieces appear in order, or (13 November) when every `...` piece's words appear in the chunk in the same order within twice the piece length plus 20 words, Markdown marks ignored (pieces need 3+ words with `...`, otherwise 4+). One rejected hop makes its dependents `unresolved_dependency`; the rejected quotes are not saved, only `reason`. The grader may invent the tail of a chunk ID after copying its first 8 characters (seen once); nothing repairs that yet.
- Routing after grading: stop reason -> `generate`; a valid grader `next_query` -> `next_hop` (copies it into `subQueries`, no AI call) -> `retrieve`; otherwise `rewrite` (fast task) -> `retrieve`, or `generate` on stop. `nextPendingHop()` picks the first unresolved hop whose dependencies are resolved, which can be the same hop again. Stop reasons: `complete`, `round_limit` (`MAX_CRAG_LOOPS`), `no_progress` (two rounds without a new resolved hop), `no_new_query`, `invalid_query`, `query_planning_failed`. Grader failure keeps up to `GRADER_FALLBACK_CHUNKS`.
- Follow-up queries use the planner's object shape (7 November). `SEARCH_OBJECT_RULES` (top of `crag.service.js`, generic examples only) is shared by the grader and rewriter prompts; it also says not to copy codes or names from already-resolved tasks. The grader returns `next_query: { hopId, text, keywords, identifiers, entities }`; `chooseFollowUp()` reads `text` (old `query` still accepted) and returns a string (`missingQuery`), and the grade node stores the full object as `nextQuery` (state field, also emitted in `grading_result`). `next_hop` sends `state.nextQuery` to `retrieve`. The rewriter (fast task, `response_format: json_object`) returns the same object, parsed with `JSON.parse` and `toSearchQuery()`; non-JSON replies become `invalid_query`. Both emit `searchTiers` in the Query Rewriter `tool_finish`. AI fills identifiers/entities; no code extracts codes from text.
- `toSearchQuery()` (`hop-evidence.service.js`) runs `cleanSearchQuery()` on `text` (one line, at most 150 characters and 20 words, no `|`) and cleans the three lists; it returns null when the text is invalid. The rewriter emits the raw reply as `rawQuery`.
- The grader prompt's JSON example shows `"status":"resolved or pending"`. Any other status (e.g. a model-invented `"unresolved"`) is labelled `invalid_task_result` by `validateGradeResponse()`; the hop simply stays pending.
- Chat history (`getChatHistory()`) is loaded before the current question is saved. It holds the last 6 messages: the newest 4 (two question/answer pairs) up to 3,000 characters each, older ones cut to 200 characters, with bracketed citations containing `Source ID` or `Page N` removed (10 November; their document titles carried codes the planner copied). The planner and the final answer both receive it.
