## Project map

- This repository is a Node.js ES-module Express backend for chat over uploaded documents. There is no frontend here. `server.js` mounts `/api/auth`, `/api/documents`, `/api/chat`, `/api/roles`, `/api/users`, `/api/health`, `/api/pipeline`, `/api/architecture`, and `/mcp` (MCP server, added 17 November), and starts the document worker.
- Code is organized as `src/routes` -> `src/controllers` -> `src/services` -> `src/repositories`; `src/config` holds clients and infrastructure; `src/utils/http.js` has `httpError(status, message)` and the `handle()` controller wrapper used by roles, users and chat conversations. Auth uses JWT via `src/middlewares/auth.middleware.js` (`requireAuth`, `requireAdmin`).
- Ingestion: upload to Supabase Storage, enqueue a BullMQ job in Redis, then `src/workers/document.worker.js` extracts pages, creates parent/child chunks, embeds child chunks, stores them in PostgreSQL/pgvector, and summarizes the document. Progress uses Redis Pub/Sub and SSE.
- Chat: `src/services/chat.service.js` runs an input security check, loads history, invokes the LangGraph corrective RAG pipeline in `src/services/crag.service.js`, and streams an answer through SSE. Search, neighbor expansion, and conversation persistence live in `src/repositories/chat.repository.js`. Hop-plan helpers live in `src/services/hop-evidence.service.js`.
- Agents (14 November): `src/agents/web/` holds the web research agent (`web.tools.js` Tavily tools, `web.agent.js` plain loop and shared prompt/helpers, `web.graph.js` LangGraph version used by CRAG). `src/config/checkpointer.js` is the LangGraph Postgres checkpointer (schema `langgraph`). See "Web research agent and approval" below.
- MCP (17 November): `src/mcp/mcp.server.js` (the MCP server: tools, progress, approval form), `src/routes/mcp.routes.js` (`/mcp`, sessions) and `src/mcp/mcp.client.js` (MCP client used by the web agent). See "MCP server and client" below.
- Database schema and migrations are in `prisma/`; Prisma Client is generated into `generated/prisma`. `src/config/db.js` uses the PostgreSQL driver adapter. Follow `PRISMA_WORKFLOW.md` for approved schema changes.
- For deeper context, read only the relevant sections of `PRODUCT.md`, `docs/chat-pipeline.md`, and `docs/delete-document-api.md`. Treat docs as orientation and verify details against current code.
- `npm test` is a placeholder that exits with an error; use relevant targeted tests when changes are authorized. `tests/crag-multi-hop.test.js` has 8 known failures (13 November): its search stub expects plain-string queries and its rewriter mocks return plain strings. `tests/hop-evidence.test.js` passes 17 of 17.

### Hybrid search (`chat.repository.js`)

- A search query is a `{ text, keywords, identifiers, entities }` object (planner, grader `next_query`, and rewriter all produce this shape) or a plain string (eval scripts and fallbacks). `buildSearchTiers()` (exported) converts either form into:
  - `idPatterns`: identifiers of at least 3 characters as `%ID%` patterns.
  - `phraseQuery`: entities as adjacent-word tsquery phrases, e.g. `(new <-> zealand) | (audit <-> committee)`.
  - `wordQuery`: planner keywords, or every useful word of the text when no keywords are given, sanitized by `buildRelaxedTsQuery()` (stop words removed, terms joined with `|`, empty string when nothing useful remains).
- `searchSingleDocument()` and `searchAllUserDocuments()` run four child-level tiers, skipping a tier whose input is empty: vector (pgvector cosine distance), identifier (`"searchText" ILIKE ANY(...)`), phrase, and keyword (both `to_tsquery('english', ...)` ranked by `ts_rank_cd`). Each tier sorts by rank before its `LIMIT`. Table-of-contents chunks (`is_toc`) are excluded. This is not BM25.
- Weighted RRF with k=10 in both functions sums per parent: vector 1.0, identifier 2.5, phrase 1.5, keyword 1.0. The top `SEARCH_PARENT_CANDIDATES` parents are returned (all-documents search uses at least 20 candidates and tier limits of at least 30). All-documents search only uses `COMPLETED` documents from the `allowedDocumentIds` list passed in by chat (see Users, roles and document access).
- The final `SELECT` orders parents by `total_score`, so the Cohere-failure fallback (`chunks.slice(0, topN)`) keeps the best-scored candidates. Each candidate carries per-tier ranks (`vectorRank`, `identifierRank`, `phraseRank`, `keywordRank`) and `matchedBy`; counts are cast to `::int` to avoid BigInt serialization errors.
- Known limits: the identifier tier has no index, and its `ROW_NUMBER()` is ordered by child ID rather than relevance. Because `searchText` includes the filename prefix, an identifier that appears in a filename matches every chunk of that file.

### CRAG (`crag.service.js`)

- `analyze_intent` routes greeting -> `generate`, summary -> `fetch_summary`, page -> `fetch_page`, and other questions -> `decompose`.
- `decompose` (agent task) returns a hop plan (at most 12 hops with `dependsOn`) and starting queries. Rule 7 ("one hop = one lookup", added 7 November, reworded 8 November) splits the question at every relationship; when the question asks for a person's name, the hop that finds the person is worded "(the person's name, not only the role)" instead of adding a separate name hop, and optional "if needed" hops are forbidden. Its worked example (ticket T-88 -> team -> manager -> email) is deliberately unrelated to any test document. Rule 10 (8 November) says "who had to / must / is allowed to approve" questions need the case's deciding value plus the rule table, then an apply hop (generic PO-7731 example). Rules added 10-13 November: rule 2 (history only resolves references; do not copy codes, titles or answers from earlier replies), rule 6 (a starting query for every entry-point task), rule 7's exception (when the answer comes from a rule or limit table, add a last hop "find the person who held the role on the case's date"), rule 10's wording (rule tasks and queries use the rule document's words, without the case's category, amount or date, shown by a starting-query example "sign-off limits by value"), rule 11 (a rule check needs a rule hop, a facts hop and a compare hop, each naming the kind of value), rule 12 (a value the user states is a given, not a lookup; its example h1 is "find the purchase approval limits by value"), rule 13 (19 November: eligibility and entitlement questions such as "will I get the bonus" get one hop per kind of condition plus a last apply hop; facts the user stated earlier in the chat count as givens; generic leave carry-forward example; added because bonus questions were planned as one hop that both found the rule and decided the case). Models followed the examples, not the sentences. `getLeavePlanningInstructions()` is no longer used in any prompt (its import in `crag.service.js` is unused). Prompt rule 15 (rule 13 before 14 November, rule 14 before 19 November) asks for `hopId` (the entry task the query is for), a short standalone `text`, 2-6 `keywords` without vague words, `identifiers` that name one record (not P1, clause, amendment or version labels), and multi-word `entities` without the asker's own company, with one worked example. Responses are normalized to objects (plain strings are still accepted) and entries without text are dropped. When the planner tags queries with `hopId`, code adds a query (the task text, first 20 words) for any entry hop without one, and puts one query per entry hop first; then queries are deduplicated by `queryKey(text)` and capped at `MAX_SUB_QUERIES` (3), so a fourth entry hop waits for a later round. There are two planning attempts; failure routes to `generate` with a `planning_failed` reply and never searches the raw question.
- `retrieve` runs all queries in parallel (`Promise.all`). Query `text` is used for the embedding, Cohere rerank, events, `allQueries`, and `searchRounds`. Only the repository receives the full object. Cohere (`rerank-english-v3.0`) reranks whole parent `searchText` to `RERANK_TOP_N` per query, ignoring search scores, and falls back to top search hits on failure. It returns scores only for the kept chunks. Collected parents keep Map insertion order, which depends on which parallel query finished first.
- `getParentNeighbors()` expands the first `EXPANSION_SEED_COUNT` collected parents, capped at `MAX_TOTAL_CHUNKS_PER_ROUND`. Each added parent records the expansion type in `retrievalOrigin.type`: `section_sibling` (prev/next), `section_lead` (when `section_part_index > 0`), `chapter_expansion` (when the question mentions process/step/flow/procedure/overview/policy/guide/sop), `table_continuation` (`table_ids`/`linked_table_ids`), and `reference_following` (only for override references like appendix/amendment, references cited in the question, or relevant table-of-contents/guide lines).
- `grade` (agent task) evaluates every hop in one batch and returns `relevant_chunk_ids`, per-hop `status`/`value`/`inputBindings`/`evidence` (chunk ID plus quote), and `next_query`. A LATER CHANGES rule also keeps chunks that amend or supersede a fact the question asks about, without changing the hop value; the answer prompt's precedence rule explains both. Rules added 10-13 November: VALUE KIND (a deadline is not an event date, a role is not a person, a count comes from the case's records), CURRENT SOURCE (use the version in force on the case's date), and exact quotes (whole lines in order, no added brackets or reformatting). Since 13 November the grader sees every chunk kept in earlier rounds (`accumulatedDocs`) plus the new round's chunks, so a hop whose facts arrive in different rounds can resolve; its input no longer contains `documentId` (it had cited a document ID as a chunk ID). The answer prompt gets a code-built VERIFIED ANSWER FACTS list (every resolved hop value, chain ends marked FINAL) just before the documents.
- `updateHopProgress()` in `hop-evidence.service.js` accepts a resolved hop only if `value` is non-empty, its dependencies were accepted, `inputBindings` match the dependency values (kept on purpose), at least one quote names a chunk the grader saw (quotes with unknown chunk IDs are dropped since 13 November; only valid quotes are stored), and every remaining quote passes `isQuoteInDocText()`. A quote passes when it is an exact normalized substring, when at least 80% of its line/`...` pieces appear in order, or (13 November) when every `...` piece's words appear in the chunk in the same order within twice the piece length plus 20 words, Markdown marks ignored (pieces need 3+ words with `...`, otherwise 4+). One rejected hop makes its dependents `unresolved_dependency`; the rejected quotes are not saved, only `reason`. The grader may invent the tail of a chunk ID after copying its first 8 characters (seen once); nothing repairs that yet.
- Routing after grading: stop reason -> `generate`; a valid grader `next_query` -> `next_hop` (copies it into `subQueries`, no AI call) -> `retrieve`; otherwise `rewrite` (fast task) -> `retrieve`, or `generate` on stop. `nextPendingHop()` picks the first unresolved hop whose dependencies are resolved, which can be the same hop again. Stop reasons: `complete`, `round_limit` (`MAX_CRAG_LOOPS`), `no_progress` (two rounds without a new resolved hop), `no_new_query`, `invalid_query`, `query_planning_failed`. Grader failure keeps up to `GRADER_FALLBACK_CHUNKS`.
- Follow-up queries use the planner's object shape (7 November). `SEARCH_OBJECT_RULES` (top of `crag.service.js`, generic examples only) is shared by the grader and rewriter prompts; it also says not to copy codes or names from already-resolved tasks. The grader returns `next_query: { hopId, text, keywords, identifiers, entities }`; `chooseFollowUp()` reads `text` (old `query` still accepted) and returns a string (`missingQuery`), and the grade node stores the full object as `nextQuery` (state field, also emitted in `grading_result`). `next_hop` sends `state.nextQuery` to `retrieve`. The rewriter (fast task, `response_format: json_object`) returns the same object, parsed with `JSON.parse` and `toSearchQuery()`; non-JSON replies become `invalid_query`. Both emit `searchTiers` in the Query Rewriter `tool_finish`. AI fills identifiers/entities; no code extracts codes from text.
- `toSearchQuery()` (`hop-evidence.service.js`) runs `cleanSearchQuery()` on `text` (one line, at most 150 characters and 20 words, no `|`) and cleans the three lists; it returns null when the text is invalid. The rewriter emits the raw reply as `rawQuery`.
- The grader prompt's JSON example shows `"status":"resolved or pending"`. Any other status (e.g. a model-invented `"unresolved"`) is labelled `invalid_task_result` by `validateGradeResponse()`; the hop simply stays pending.
- Web hops and approval (14 November): the planner gives every hop `source: "documents" | "web"` (rule 14 since 19 November, rule 13 before); `decompose` keeps document hops in `hopPlan` and web hops in `webHops`, so the grader and completion checks never see web hops. When the document loop stops (any stop reason), or right after planning when the plan has only web hops, `routeToAnswer()` goes to `ask_approval` if `webHops` is non-empty and the user has not answered yet, else to `generate`. `ask_approval` -> `web_agent` (Allow) or `generate` (Skip); `web_agent` -> `generate`. Details under "Web research agent and approval".
- Chat history (`getChatHistory()`) is loaded before the current question is saved. It holds the last 6 messages: the newest 4 (two question/answer pairs) up to 3,000 characters each, older ones cut to 200 characters, with bracketed citations containing `Source ID` or `Page N` removed (10 November; their document titles carried codes the planner copied). The planner and the final answer both receive it.

## Web research agent and approval (ROADMAP Step 5, built and verified 14 November)

- Terms: CRAG is a code-driven agentic workflow (code picks the next node). The web research agent is an AI agent (the model picks tools in a loop). Several web agents can run at once, one per web task; that is parallel agents of one kind, not a supervisor/multi-agent system (Step 5B).
- Tools (`web.tools.js`; since 17 November these are only the fallback, the agent normally uses the Tavily MCP tools, see "MCP server and client"): `web_search({ query })` (Tavily `/search`, 5 results: title, URL, text cut to 600 characters, published date) and `read_page({ url })` (Tavily `/extract`, text cut to 6,000 characters). Plain `fetch`, `TAVILY_API_KEY`, 20-second timeout. `webTools` maps each tool name to `{ definition, run }`.
- Loop: `web.agent.js` exports `MAX_STEPS` (4), `SYSTEM_PROMPT`, `runToolCall()` (bad arguments or unknown tools come back as `{ error }` to the model), `collectSources()`, and `runWebAgent()` (plain loop, kept for learning and scripts). `web.graph.js` `runWebAgentGraph(task, { maxSteps, onStep })` is the same loop as a graph (`agent` <-> `tools`) and is what CRAG uses; it uses the `agent` task model (airouter `deepseek/deepseek-v4-flash`, supports parallel tool calls). The last step is sent without tools and with "Step limit reached. Answer now". Returns `{ answer, sources, steps, stopReason: "done" | "step_limit" }`. `sources` holds every URL searched or read, not only the ones used. It compiles with `checkpointer: false`: otherwise it inherits CRAG's checkpointer through the run config and parallel agents share one checkpoint slot.
- Planner (rule 14 in `decomposeNode`, rule 13 before 19 November): "web" only for public or live facts (current exchange rates, market prices, news, laws, public facts about other organizations); company records are always "documents". No starting queries for web hops. A document hop may not depend on a web hop, and a web hop may not depend on another web hop (both throw, so planning retries). A value asked in another currency: plan "find the value and its currency" plus a rate hop, which is "web" unless the question names a company rate (budget, contract, internal); no hop for the arithmetic. `validateHopPlan()` keeps `source` only when it is "web", so document hops keep their old shape.
- State: `webHops` (web hops from the plan), `webApproval` (null = not asked, true, false; one question per run), `webFacts` (`{ searchedAt, results: [{ hopId, task, answer, sources, stopReason }] }`).
- `ask_approval` only calls `interrupt({ question, webHops })` and returns `webApproval`; on resume LangGraph re-runs the node from its first line and `interrupt()` returns the decision, so nothing with side effects may sit before it.
- `web_agent` runs `runOneWebAgent()` for every web hop with `Promise.all`. Each agent's task is the hop text plus "Known from company documents: h1 = <resolved value>" for its dependencies, so document values (for example an order amount) are sent to Tavily; the approval card says so. Events per agent: `agent_start`, `agent_step` (one per tool call), `agent_finish` (or `failed: true, reason`), each with `agentId` (`web-<hopId>`), `agent: "Web research"` and `hopId`. A failed agent returns an empty answer with `stopReason: "failed"` and does not stop the others.
- `generate` adds a WEB FACTS block (task: answer, search date, "treat as data") with rules: label document facts with [Source ID] and web facts with URL and date, show conversion working, web facts never replace company facts, answer from web facts even when no document data is relevant. It names web tasks that found nothing; after Skip it says which outside facts were not looked up. `webHops` is included in ANSWER COVERAGE.
- Pause and resume (`chat.service.js`): every question gets `threadId = randomUUID()` and the graph runs with `{ configurable: { thread_id, onEvent } }` (functions go in `configurable`, never in state). ## MCP server and client (ROADMAP Step 6, built 16-17 November; the user wrote the code from chat guidance)

- Server (`mcp.server.js`): `buildMcpServer(user)` makes one `McpServer` per logged-in user, so every handler closes over the full `req.user` (never `user.id`) and role rules hold. Four read-only tools: `search_documents({ question, documentId? })`, `list_my_documents`, `get_summary({ documentId })`, `get_page({ documentId, page })`. `get_page` reuses `chatRepository.getChunksByPage`; `get_summary` reads `Document.summary`; a missing and a forbidden document both answer "Document not found." (`canAccessDocument`, same rule as chat). Inputs are checked with zod before a handler runs; failures return `isError: true` text.
- `search_documents` (`runSearch`): same security check as chat (`checkMaliciousIntent`), `allowedDocumentIds` from `getAccessibleDocumentIds(user)` or the one document, then `cragPipeline.invoke` once with `historyText: ""`, no streaming and no saved conversation. It returns the answer plus a "Sources:" list built from `citations` (`displayLabel`, `documentId`). A fresh `thread_id` is used per call and its checkpoints are deleted in `finally`.
- Progress: `createProgressSender(extra)` passes CRAG events as `configurable.onEvent`; only `tool_start`, `status` and `agent_start` become `notifications/progress` (message text, a rising `progress` number, no `total`), and only when the client sent a `progressToken`.
- Web approval over MCP (A6, done differently from the roadmap text): when CRAG pauses on `interrupt()`, `askWebApproval()` uses `server.server.elicitInput()` (a form with one boolean "Allow web search", sent on the same request with `relatedRequestId`, 5-minute timeout) and resumes with `new Command({ resume: { approved } })` on the same `threadId`, which stays in a local variable (no `threadId` goes to the client). A client without the elicitation capability, a decline, a cancel, an error or a timeout all resume with `approved: false` and the answer carries a note that the web search was skipped.
- Route (`mcp.routes.js`): Streamable HTTP with sessions. `POST /mcp` without `Mcp-Session-Id` must be `initialize` and creates a server and transport (`sessionIdGenerator: randomUUID`); the transport is kept in an in-memory `sessions` Map with the owner's `userId`, and a request whose `req.user.id` differs gets 404. GET opens the server-to-client stream, DELETE ends the session. A restart drops all sessions; clients reconnect. The sessions are why elicitation works (the client's answer arrives as a second request); several server instances or serverless hosting would break them.
- Auth: `requireAuth` runs on every `/mcp` request with the same Bearer JWT as the REST API (7-day token), so inactive users are blocked at once and roles are re-read on each tool call. No per-user MCP tokens, revoking, audit table or OAuth (roadmap A2 inactive). Without a token the answer is 401; clients that expect OAuth then call `/register` and fail with 404. Claude Code (`claude mcp add --transport http ... --header "Authorization: Bearer <token>"`), Claude Desktop through `mcp-remote`, and MCP Inspector work; ChatGPT and claude.ai custom connectors need OAuth 2.1 and are not supported.
- Not built (roadmap `[-]`): resources, prompts, sampling and completions, list-changed notifications, audit log, logging notifications, clarifying questions.
- Client (`mcp.client.js`): `MCP_SERVERS` lists the servers (today only `tavily`: `https://mcp.tavily.com/mcp/`, Bearer `TAVILY_API_KEY` from env, `allowedTools: ["tavily_search", "tavily_extract"]`, `maxChars: 6000`). `getMcpTools(name)` connects once (a cached Promise per server; a failed connect or a failed `listTools()` drops the cache so the next call reconnects), lists the tools at run time and returns `{ [toolName]: { mcpServer, definition, run } }`, the same shape as `webTools`; `inputSchema` becomes the model's `parameters`, and `run` returns `{ text }` (text blocks joined and cut) or `{ error }` when the server says `isError`. Tavily also offers `tavily_crawl`, `tavily_map` and `tavily_research`; they are left out on purpose (slow and costly for a 4-step agent).
- Web agent change: `runWebAgentGraph` calls `loadWebTools()` (`web.graph.js`): MCP tools first, the built-in `web.tools.js` (`web_search`, `read_page`) when the MCP server is unreachable, with a console error. The registry travels in `config.configurable.tools`, and `runToolCall(call, tools = webTools)` and the model's tool list use it. `collectSources` also reads URLs from MCP text results (first 10 per result). `agent_step` events carry `mcpServer` (`"tavily"` or `null`). The approval rule is unchanged: nothing reaches Tavily before Allow (chat UI) or the elicitation "yes" (MCP).
- Verified 16-17 November: Inspector (tools, a normal user sees fewer documents, progress messages, approval form; its request timeout must be raised to 300000 ms because CRAG takes 20 s to 2 minutes), and a web question in the chat UI with `tavily_search` steps. A Claude app connected to the live server chose `search_documents` by itself and answered a purchase-order question from the documents (17 November). Not confirmed: Decline in the approval form, and the built-in fallback when the MCP server is down.
- Known limits: the planner still only knows `documents` and `web`; MCP tools are not chosen per hop (roadmap B3/B4 inactive); `search_documents` has no chat history, so a client must send a standalone question.
